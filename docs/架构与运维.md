# 架构与运维手册

写给要改这个项目、或者线上出问题要查的人。目标不是"介绍功能"，而是
**两页之内建立全局观**，然后能直接定位。

功能说明看 [README](../README.md)，API 契约看 [API 文档](../API文档.md)。

---

## 1. 数据流全景

```
PS5 (GT7)
   │  UDP 广播，60 帧/秒，Salsa20 加密
   │  目标 255.255.255.255:33740（本地 33739 发心跳）
   ▼
gt7-recorder ──────────────────────────────────────────────┐
   │                                                        │
   │ ① 收包 + 解密                                          │
   │    gt7-decrypt（Go 子进程）：hex 进 → hex 出            │
   │    也可以用内置的纯 Python 实现（慢，调试用）           │
   │                                                        │
   │ ② 按包长判定布局：296=A / 316=B / 332~344=~ / 368=C    │
   │    ↓ 按偏移表解成 TelemetrySample（dataclass）          │
   │                                                        │
   │ ③ 两个出口                                              │
   │    ├─ data/YYYYMMDD_HHMMSS_<赛道>_<hash>.jsonl          │
   │    │    每帧一行，正式数据，**不能丢**                  │
   │    └─ data/status.json                                  │
   │         给仪表盘读的实时快照，schema 2 增量协议         │
   ▼                                                        │
gt7-dashboard（HTTP :8787）                                 │
   │                                                        │
   │ ④ TelemetryHub 读 status.json，按 q 续接 600 帧环形缓冲│
   │    （后台线程 10Hz 刷新，不阻塞请求）                  │
   │                                                        │
   │ ⑤ 分析层 gt7analysis（纯函数，无 IO）                  │
   │    圈速 / 分段 / 走线偏差 / 滑移 / 赛道指纹            │
   │                                                        │
   │ ⑥ 出口                                                  │
   │    ├─ HTML 页面（实时 / 历史 / 赛道 / 回收站）          │
   │    └─ /api/v1/*（38 个端点，带 CORS）                   │
   └────────────────────────────────────────────────────────┘
```

**一句话**：recorder 负责"把 UDP 变成两个文件"，dashboard 负责"把两个文件
变成页面和 API"。两者之间**只通过文件系统通信**，没有网络调用、没有共享内存。

这个边界很重要：recorder 挂了不影响看历史，dashboard 挂了不影响继续录。

## 2. 模块边界

| 文件 | 职责 | 明确**不该**做的事 |
|---|---|---|
| `gt7-recorder.py` | 收包、解密、解析、落盘、写 status.json | 不做分析（不算圈速、不判事件） |
| `gt7-dashboard.py` | HTTP 服务、读文件、调分析、渲染页面 | 不写 jsonl（只写 tracks/settings/meta 这些元数据） |
| `gt7analysis.py` | 纯函数分析库 | **不做任何 IO**——不读文件、不写文件、不碰网络。所有数据由调用方传入 |
| `gt7-event-detector.py` | 事件检测（9 类） | 不读文件；`Sample` 由 dashboard 从帧转换后传入 |
| `gt7_version.py` | 唯一版本源 | 不 import 任何项目内模块（避免循环依赖） |
| `gt7-decrypt/` | Go 解密器 | 只管 hex→hex，不理解字段语义 |
| `tools/` | 运维脚本（部署 / CHANGELOG / lint） | 不被运行时 import |

**为什么 `gt7analysis.py` 必须无 IO**：它是最容易写测试的一层，94% 覆盖率
全靠这个约束。一旦它开始自己读文件，"给一组人造帧验证算法"就做不到了。

**为什么 `gt7-event-detector.py` 用文件名加载**：文件名有连字符，不能
`import`。dashboard 用 `importlib.util.spec_from_file_location` 按路径加载。
⚠️ 打包成 exe 时 `--add-data` 必须带上它，否则 `/events` 与 `/highlights`
静默变成"不可用"（`--hidden-import` 管不了，它不是 import 出来的）。

## 3. 三个最容易踩的机制

### 3.1 场次切分：什么时候算"这一场结束"

`gt7-recorder.py` 有**三个**独立的结束条件，命中任一个就收尾并开新文件：

| 条件 | 代码位置 | 典型场景 |
|---|---|---|
| 帧间隔超过休眠阈值（`_gap_before_batch`） | 处理每批数据时 | 主机休眠 22 小时后唤醒 |
| 空闲超过 `--session-gap` 秒（默认 10） | 主循环 | 退出赛道回菜单 |
| 圈号从 ≥3 回落到 ≤1 | `_handle_sample` | 菜单里重新开一局 |

**为什么要三条**：只靠空闲超时的话，主机休眠期间不产生帧，唤醒后第一帧
会接着上一场写——两场比赛混进同一个 jsonl，圈号从 15 跳回 1，圈速全乱
（实测出现过 149%~362% 的"假圈"）。

⚠️ **顺序陷阱**：`_gap_before_batch` 必须在刷新 `last_active` **之前**调用。
顺序反了，间隔在检查时已经变成 0，休眠检测永远不触发。

### 3.2 `status.json`：schema 2 增量协议

仪表盘按 10Hz 轮询，遥测是 60Hz。如果每次都写完整缓冲，**曲线只剩 1/6 的点**
（早期版本的真实 bug）。

现在的协议：

```jsonc
{
  "schema": 2,
  "seq": 12345,          // 写入次数
  "q": 6789,             // 帧序号（单调递增，只有新帧才 +1）
  "t": 1792610000.0,
  "frame": { ... },      // 最新一帧
  "history": [ ... ],    // 最近 60 帧的增量（不是 600）
  "full": [ ... ]        // 每 20 次写附带一次完整 600 帧
}
```

**读法**：拿到 `q`，只取 `q > 自己上次 q` 的帧接到自己的缓冲里。
`q` 不连续说明中间有丢包 → 等下一次 `full` 自愈，或主动请求
`GET /api/state?full=1`。

**两个必须知道的细节**：

- `new_frame=False`（游戏暂停时 PS5 重复发同一帧）只刷新 `last_rx_t`，
  **不推进 q、不进缓冲**。所以"暂停时 `last_packet_age` 一直为 0 但
  `q` 不动"是正常现象，不是 bug。
- `t` 用的是**最后一帧新数据的时间**（`_last_frame_t`），不是收包时间。
  否则暂停时 `t` 还会往前走，前端会画出一段"速度不变但时间在流逝"的假曲线。

### 3.3 三层缓存：各自防的是什么

| 缓存 | 位置 | 失效条件 | 防的问题 |
|---|---|---|---|
| **帧缓存** `_FRAMES_CACHE` | 内存，上限 320MB | 按字节淘汰（LRU） | 每次请求都重新解析几十 MB 的 jsonl |
| **场次索引** `session_index.json` | 磁盘，`data/` 下 | `(mtime, size)` 任一变化 | **容器重启后**重新解析全部场次算最快圈（实测 72 场 / 520MB → 25 秒） |
| **memo** `store.memo_compute` | 内存，按场次 | 场次 + 参数指纹 | 事件检测（冷路径 ~10s）、分段计时 |
| **参考走线** `ref_lines.json` | 磁盘，`data/` 下 | 手动重建（POST） | 每次要看"和我的典型走线差多少"都重算 8 场最快圈（几十秒） |

**为什么场次索引必须落盘**：帧缓存和 memo 都是进程内的，容器一重启就全丢。
而"每个场次的最快圈"必须完整解析文件（最快圈可能在任意一帧），
72 个场次就是 25 秒白屏。索引按 `(mtime, size)` 双判据缓存——只看 mtime
会被"同一秒内改写"骗过，只看 size 会被"等长覆盖"骗过。

**memo 的 key 里为什么要带阈值指纹**：事件阈值可以在页面上改。如果 key 只有
`("events", lap_no)`，改完阈值再打开事件卡会**命中旧缓存**，用户以为"改了没用"。

## 4. 故障排查：症状 → 原因

### 4.1 实时页没有数据 / 一直显示"未连接"

按顺序查：

```bash
# ① 容器活着吗
docker ps --filter name=gt7

# ② 收包了吗（last_rx_age 是距最后一次收到任何 UDP 包的秒数）
curl -s localhost:8787/api/health | python3 -m json.tool

# ③ 心跳发出去了吗（recorder 日志里应有"目标 N 个"）
docker logs --tail 50 gt7-recorder
```

| 症状 | 原因 | 处理 |
|---|---|---|
| `last_rx_age` 很大（>60） | PS5 没发、或网络不通 | 确认 PS5 的"遥测上传"已开；确认两边同一网段；`network_mode: host` 必须开（bridge 收不到广播） |
| `last_rx_age` 正常但 `frames` 不涨 | 收到了但解不开 | 看日志有没有 `bad` 计数；固件升级后密钥可能变（A4 项，目前无解） |
| `frames` 在涨但页面不动 | 前端没拿到新帧 | 看 `/api/state?full=1` 是否返回数据；检查浏览器控制台 |
| 页面显示"未连接"但 `/api/health` 说 `connected: true` | 浏览器缓存了旧页面 | 强制刷新（Ctrl+Shift+R） |

⚠️ **`connected: false` 不代表故障**。PS5 关机、回菜单、暂停都会让它变 false。
告警要看 `last_rx_age`，不要看 `connected`（`/metrics` 里刻意没有暴露
`gt7_connected` 这个 gauge，就是为了避免这种误告警）。

### 4.2 「历史场次」页转圈 / 很慢

**先量一下**：

```bash
curl -s -o /dev/null -w '%{time_total}s\n' localhost:8787/sessions
```

| 耗时 | 判断 |
|---|---|
| < 0.5s | 正常 |
| 1–5s | 有新的场次文件还没进索引（每个文件 1–3 秒），等预热跑完 |
| > 10s | 索引缺失或损坏，见下 |

```bash
# 索引有多少条（应该接近场次文件数）
python3 -c "import json;print(len(json.load(open('/opt/gt7-recorder/data/session_index.json'))['sessions']))"

# 场次文件数
ls /opt/gt7-recorder/data/*.jsonl* | wc -l
```

索引条数明显少于文件数 → 删掉 `session_index.json` 让它重建，或重启容器
（启动时后台线程会自动预热）。

### 4.3 参考走线的「圈间差」很大

`/tracks` 页点「生成参考走线」后，如果显示的圈间差（`spread_m`）超过 10m：

| spread | 判断 |
|---|---|
| 1–3m | 正常。不同圈本来就有差异，这就是"你的走线抖动" |
| 3–10m | 偏大。可能有暖胎圈/失误圈混进来了，或车不同 |
| > 10m | **这些圈不是同一条走线** —— 多半是赛道识别把两条赛道认成一条了 |

先看 `sources[]` 里每场的圈速和圈长：圈长差超过 3% 的会被自动剔除，
但 3% 以内的"慢很多但长度一样"（比如半湿赛道）剔不掉，只能人工判断。

重建方法：`POST /api/v1/tracks/<id>/ref-line`，或点卡片上的「重建」。

### 4.4 圈速和游戏里显示的不一致

**先确认看的是哪个口径**。列表页和详情页都优先用 GT7 官方的 `last_lap_ms`，
只有官方值缺失时才回退到帧跨度。

```bash
curl -s "localhost:8787/api/v1/laps" | python3 -m json.tool | head -30
```

看 `time_source` 字段：

| 值 | 含义 |
|---|---|
| `official` | 来自 GT7 的 `last_lap_ms`，可信 |
| `span` | 帧跨度（末帧时刻 − 首帧时刻），**会把暂停/进站期间算进去** |

如果 `time_source` 是 `span` 而游戏里有官方值，说明该圈的官方值没被捕获
（换圈那一帧丢了）。这是数据问题，不是算法问题。

**已知的假圈来源**（都会被 `lap_is_complete` 挡掉）：

- 残圈 / 中途退出：实测 3.4%~61.2% 圈长
- 时钟跳变：149%~362%（主机休眠把两场比赛塞进同一文件）
- 滚动发车的出场圈：约 117%（**这个会被保留**，它在 90%~125% 区间内）

### 4.5 事件不对（漏报 / 误报）

先分清是**数据**问题还是**阈值**问题：

```bash
# 看这一场检测出了什么
curl -s "localhost:8787/api/v1/sessions/<文件名>/events" | python3 -m json.tool | head -40
```

| 现象 | 最可能的原因 |
|---|---|
| 进站被报成"长时间低速"（置信度 0.5） | 没抓到加油信号。油箱已满的进站**无法**和暂停区分，这是协议限制，宁可不报 |
| 超车漏报 | 名次变化被防抖吃掉了（`position_hold_s` 默认 0.5s）；或 `quali_pos` 是 65535 哨兵（计时赛/菜单） |
| 打滑大量误报 | `spin_lat_g` 阈值偏低，页面事件卡里可以直接调 |
| 事件卡改了阈值没变化 | 不应该发生（阈值指纹进了 memo key）。若发生，检查 `POST /api/v1/settings/event-thresholds` 是否成功 |

### 4.6 磁盘占满

```bash
du -sh /opt/gt7-recorder/data/
docker system df
```

三个来源，各有各的处理：

| 来源 | 排查 | 处理 |
|---|---|---|
| 场次文件（占大头） | `ls -lS data/*.jsonl* \| head` | 归档会自动压成 `.jsonl.gz`（省 95%）；也可以在页面上删 |
| 容器日志 | `docker logs gt7-recorder 2>&1 \| wc -c` | compose 里已设 `max-size: 10m` / `max-file: 3`，正常不会超 30MB |
| 旧镜像 | `docker images \| grep gt7` | `docker image prune` |

## 5. 部署与回滚

```bash
# 正常部署（从 ghcr 拉镜像）
GT7_IMAGE=ghcr.io/dc1024/gt7-dash:v1.4.3 \
  docker compose up -d --no-deps --force-recreate gt7-recorder gt7-dashboard

# 回滚到上一个版本（镜像 tag 都在）
GT7_IMAGE=ghcr.io/dc1024/gt7-dash:v1.4.2 \
  docker compose up -d --no-deps --force-recreate gt7-recorder gt7-dashboard
```

**两条硬规则**：

1. **必须带 `--no-deps`**。compose 里的 `depends_on` 会让"重建 dashboard"
   连带重建 recorder，正在跑的比赛被切成两个文件（真实丢过 30 秒数据）。
   这也是 compose 里已经删掉 `depends_on` 的原因。
2. **部署前确认没有在录制**：

   ```bash
   curl -s localhost:8787/api/health | python3 -c \
     "import sys,json;d=json.load(sys.stdin);print('connected',d['connected'],'rx_age',d['last_rx_age'])"
   ```

   `connected: true` 就等比赛跑完再动。recorder 收到 SIGTERM 会正常收尾
   （tini 转发信号 → `_end_session()` 写文件尾），但**那一场会被切成两段**。

**版本核对**：

```bash
curl -s localhost:8787/api/health | python3 -c "import sys,json;print(json.load(sys.stdin)['version'])"
```

应该等于 `gt7_version.py` 里的 `__version__`。四处出口同源（HTTP `Server:` 头、
`/api/health`、录制文件头 `recorder_version`、README），CI 有测试盯着。

## 6. 观测

```bash
curl -s localhost:8787/metrics
```

| 指标 | 看什么 |
|---|---|
| `gt7_last_rx_age_seconds` | **最重要的一个**。持续增长 = 没在收数据 |
| `gt7_frames` | 当前环形缓冲帧数（正常是 600） |
| `gt7_frame_cache_bytes` | 帧缓存占用。接近 320MB 说明淘汰在频繁发生 |
| `gt7_sessions_total` | 历史场次文件数 |
| `gt7_uptime_seconds` | 进程运行时长。**频繁重启**说明容器在崩 |

刻意**没有** `gt7_connected`：PS5 关机是正常状态，做成 0/1 指标会让告警
天天响。用 `gt7_last_rx_age_seconds` 自己定阈值。

## 7. 改代码前必须知道的

1. **一次只改一个功能**。这个项目单文件上万行，改 5 个地方同时出 bug
   无法定位。
2. **改完立刻跑**：`python -m pytest -q`（当前 707 passed）。改前端还要
   `python tools/lint_inline_js.py _lint_js && npx eslint _lint_js`。
3. **跑通立刻提交**。AI 或自己把项目改坏了，能一键回到上一个好状态。
4. **两个文件都有大量"为什么"注释**（`🔴` 开头）。改之前先读那段——
   很多看起来奇怪的写法是踩过坑之后的结果，注释里写了踩的是什么坑。
5. **`API文档.md` 和 `gt7-dashboard.py` 里的 `API_DOCS_MD` 是两份副本**，
   必须同步改（`tests/test_api_docs_sync.py` 会检查）。
